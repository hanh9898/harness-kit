# Reconcile incomplete and existing onboarding

Read when records, prior applied guidance, legacy progress or uncertain effects
already exist. Find the authoritative current view and linked history from the
project's existing pointers. Inspect live state that can affect the next action.
Retain completed effects, adequate conventions, accepted scope and valid grants.

For unavailable records or uncertain writes, use [persistence recovery](../../../kit/PERSISTENCE.md) to qualify capture and reconcile per-target effects before continuing.

For failures spanning tasks, artifacts or shared prerequisites, use [coordinated recovery](../../../kit/RECOVERY.md) while retaining setup's foundation completion criteria.

Map what exists to [FOUNDATION.md](FOUNDATION.md)'s semantic outcomes. A missing
legacy directory, setup heading or step log is not missing semantic context.
Reuse adequate evidence under its original host/provider/scope conditions; assess
only affected claims after changes. Keep unknown origin or unverified behavior
visible, retaining useful personal material rather than inventing provenance.

For an interrupted write, inspect the affected target, record/history and any
active writer/lock before retry. Follow [UPDATE.md](../harness-evolve/UPDATE.md)
for shared serialization and stopped-owner recovery. Reconcile already-applied
work with missing records instead of repeating the effect; an old planned action
is not evidence that it remains unapplied or authorized. Reuse settled interview
answers; its linked design-writeback check applies only where that method was used.

For each remaining consuming target, reopen actual provider availability,
invocation policy, grants and useful checks. Complete independent authorized
work while missing access blocks only dependent effects. Preserve per-target
results and an exact next trigger. A fully satisfied live foundation needs no
new files, history events or repeated demonstration unless its evidence changed.

## Reading legacy material

[RECORD-FORMAT.md](RECORD-FORMAT.md) documents existing entry/progress fields;
[BOUNDARY.md](BOUNDARY.md) describes the old situation-card values. Their validators
remain available for those formats. A `passing` label establishes only the check
actually recorded, not current runtime readiness. Preserve adopted and
`needs-change` work, history revisions and project-built pieces. Relate useful
material to existing resources when adequate, or retain it as personal material.

Other former setup references remain for interpreting old work:
[ASKING.md](ASKING.md), [GATE.md](GATE.md), [PROPOSALS.md](PROPOSALS.md),
[DELEGATION.md](DELEGATION.md), [ROLES.md](ROLES.md),
[STANDARDS-STEP.md](STANDARDS-STEP.md), [ISOLATION.md](ISOLATION.md) and
[WIRING.md](WIRING.md). They describe historical stage/schema contracts only;
current setup selects needed outcomes through SKILL.md and the shared methods.
Preserving these references does not restore their questionnaire, delivery ladder,
mandatory folders, delegation defaults or universal wiring requirements.
