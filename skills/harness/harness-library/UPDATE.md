# Compare and update library material

Use the entry's grants, original methods and standards. Library updates change saved content; consumer adoption remains separate. Read the [operation contract](../../../kit/LIBRARY.md#origin-comparison-and-updates) for the local commands and input fields.

1. Inspect live `show`, `history`, `selection` and `selection-history`, the actual candidate source, and known uses within scope. Establish the complete selected contents, including nested children, from attributable snapshots. The local operation stores assembly contents in `content`; referenced files remain independent. If required contents or history are unavailable, name that gap. Reconcile an uncertain prior effect before retrying; a completed update needs no duplicate revision.
2. Run `compare` with the candidate's reference, revision and exact snapshot. Examine old origin versus customization, old origin versus candidate, and current selection versus candidate. Preserve unknown history as unknown. A textually clean merge is only a textual observation. Read the applicable target contract and check meaning, dependencies, applicability, authority and evidence requirements, including interactions between changes on different lines.
3. Choose the authorized result:
   - **Update:** keep valid customizations and apply independently compatible changes. For unresolved conflicts, retain the valid prior affected selection and old origin basis, record the pending candidate and remaining work as `partial`. With no safe change, record `blocked` with unchanged content. If the prior selection is invalid, block dependent use and preserve content for recovery.
   - **Replace parent:** select the complete new assembly exactly. Prior child customizations stay in history; they are not active in the replacement. Verify the new assembly's contract and prerequisites. Missing prior history remains visible even when the new assembly can be independently checked.
   - **Carry forward:** act on an explicit request to reuse historical customization. Retrieve its actual prior revision, identify the target in the new assembly and check compatibility against the new contract. Carry only the requested compatible material; preserve other new contents. If the target or contract is incompatible, keep the replacement selected and record the blocker using an ordinary blocked update.
4. Record the review before the effect: actual checks and their evidence/references, compatible changes, conflicts, unknowns, prior selection validity, authority/rationale, selected methods/standards and continuation. Use `update` with the inspected revision and comparison token. Semantic review is the caller's accountable assessment; the CLI validates structure, identity and freshness, not truth. Use original writing-for-agents for agent-read changes; a missing required method blocks dependent construction rather than authorizing silent replay.
5. Read back the saved content, selection and their histories. Updates, replacement and carry-forward preserve the resource's exclusion and its provenance; only an explicit restoration changes that choice. Verify only the authorized library selection changed, old customization remains recoverable and known consumer state is unchanged. Report complete/partial/blocked accurately, with origin/customization/candidate relationships, checks and limits. Resume from the authoritative record; unresolved candidates require a fresh comparison against live state.
