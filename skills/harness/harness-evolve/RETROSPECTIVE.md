# Learning-only retrospective

Select the current original retrospective method and inspect its invocation policy before execution. If it is explicit-only, the user must invoke that method through the supported host route; the outer evolve call alone is insufficient. Return that exact continuation when blocked. Reading its source to establish this condition does not authorize manual execution.

Once invocation is permitted, preserve the original method's full contract, including required writing guidance, primary session evidence, inspection of existing checks, classification of findings and presentation. Carry the requested session, project/kit context, effective grants and evidence limits into the method. Missing source facts remain unknown; a summary is evidence only of what it actually records.

Use `harness-library` for relevant kit summaries, selection checks and verified
details before recommendations. Compare suggestions with live facilities so a
working but unwired check is not mistaken for a missing tool. Review candidates
against the original method and applicable criteria. This reference supplies
composition boundaries, not a substitute retrospective procedure.

Deliver the requested learning with evidence and useful priority. Recommendations, proposed verification and adoption are separate: a learning-only request authorizes neither implementing a check nor editing project/global guidance. Save a retrospective only within an actual grant. Report the result first, attribute material resources and give the requested contribution trace. Show an unfollowed recommendation or missing condition when it changes the result; omit empty exception fields.

**Done:** the original method's learning result is delivered, its evidence limits are visible, and unchanged scope is verified. If an authorized save or dependent method remains blocked, retain its exact continuation without expanding the request.
