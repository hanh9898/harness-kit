# Instruction and response design

Use through setup/evolve for a direct instruction request, conflicting guidance,
an agent handoff or a recurring output contract. Deliver reconciled instructions,
usable examples and externally testable output expectations. A design can be a
complete result without adoption, a team, a workflow or tool installation.
The calling workflow retains its method, grant, pre-action record and continuation
procedure. Advice ends in the reply unless saving was granted.

## Reconcile sources before dependent use

1. Identify the consumer, requested artifact, language/content criteria, intended
   host, available source guidance and the permitted design/application scope.
   Inspect representative inputs and outputs when available. Separate source
   material to summarize from instructions the host actually treats as binding.
2. For each material rule, identify its authoritative source/revision, scope,
   owner and effective meaning. Inspect the actual applicable host precedence
   and project adoption procedure. A source's claim of priority is not evidence
   that it has that authority. Examples illustrate rules; they cannot grant
   effects or override a governing contract.
3. Reconcile each conflict using that evidence. State the competing meanings,
   the supported resolution and the authority that permits it. File proximity,
   a newer date, a stronger word or a preferred method establishes no universal
   hierarchy. Missing or unsupported precedence is an **unmet prerequisite**:
   identify the dependent rule/use, retain a valid prior selection where possible,
   and name the authoritative source or competent owner's choice needed to resume.
   Continue independent design whose meaning is settled.

**Done:** every rule needed for the requested use has a supported effective
meaning, or that use is explicitly blocked. Editing permission alone does not
resolve a separately governed contract. Follow the prior adoption procedure;
the replacement cannot authorize itself.

## Construct the result

Use the calling workflow's [original-method composition](../../skills/harness/harness-evolve/CHANGE-FLOW.md).
Load current original writing-for-agents for agent-read artifacts, including
handoffs; preserve its invocation prerequisites and applicable references.
An unavailable required provider blocks dependent authoring, not inspection or
reporting the prerequisite. Use [writing scope](WRITING.md) for the accepted
STE-inspired recommendation and [examples](EXAMPLES.md) when constructing or
checking the contract. Retrieve agent-document-conventions and relevant output resources through the
kit CLI; source certainty remains separate from observed use.

Give the consumer these meanings in its existing suitable form:

| Result part | Required usable content |
| --- | --- |
| Instructions | Trigger, required inputs/access route, effective rules with authority references, ordered actions and explicit completion/blocking conditions |
| Output contract | Audience, language, terms, content/attribution, uncertainty, form and permissible partial results; preserve the consumer's selected criteria |
| Examples | A realistic valid input/output and a plausible invalid or blocked case, with the reason and allowed next action; label invented data as illustrative |
| Acceptance checks | For each material criterion, observable expected result, inspection/check route, evidence needed and handling of failure or missing evidence |
| Continuation | Completed work, unsettled rules, actual adoption state, missing prerequisites and the next authorized trigger |

Keep each rule in one authoritative home. Reference it from examples and checks
so an example cannot silently replace the rule. Make context pointers state when
the consumer must read the source. A handoff carries relevant inputs, authority,
criteria, actual evidence and the remaining action; a method name alone is not
a usable handoff. Preserve narrower scope when only one artifact is requested.

**Done:** a consumer can act and an external reviewer can distinguish acceptable,
invalid and blocked results without guessing the author's intent.

## Check content and protocol separately

Instruction/response owns model-result content and form: supported claims,
correct values, selected language/terms, required evidence, uncertainty and
presentation. A parseable output can still fail every substantive criterion.
Check representative outputs against source facts as well as syntax. A document
schema is a content/form check when the document itself is the requested result.

Tools/integrations owns the actual exchanged protocol/data contract: operation,
arguments, envelope/schema, transport and returned status. A valid report does
not prove successful delivery; a successful exchange does not prove a correct
report. If delivery is selected, identify its actual contract, validation route,
authority and tool owner. Leave protocol validity **unverified** until inspected
or exercised at that interface. Instruction design does not install a tool or
manufacture that missing evidence.

For invalid content, stop dependent consumption and repair only within the
selected scope and stop bound. For invalid protocol, stop the dependent exchange
and hand the specific failure/evidence to its tool route; preserve valid content.
For uncertain exchange effects, inspect live state before retry. Neither failure
licenses invented missing facts, repeated delivery or unlimited regeneration.
Use existing checks before adding a checker. Editorial checks do not establish
accuracy against inaccessible sources; retain any selected human accuracy review.

**Done:** inspect actual guidance/examples and representative consumer output,
not just a claimed method load or passing wording check. Report each criterion's
observed result and limits. Keep design, application, model-output acceptance,
protocol validity and improvement claims distinct in the calling workflow's
record or advice result. A later resume inspects live artifacts and preserves
completed effects.

## Source scope

This procedure is inferred implementation guidance for accepted
[spec 15, especially 15/34–37 and A27/A31](https://github.com/hanh9898/harness-kit/issues/15)
and [ticket 23](https://github.com/hanh9898/harness-kit/issues/23).
Those sources establish the selected product contract, not host-specific
precedence or runtime qualification. result-and-brief-templates/presentation-conventions are inferred output conventions;
agent-document-conventions remains open catalog guidance. The current original writing method supplies
the authoring discipline. Local examples and checks operationalize the accepted
contract; their acceptance does not certify a standard or establish another
host's behavior. Preserve actual method/version, source certainty, grants and
test conditions with the evidence.
