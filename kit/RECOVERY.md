# Coordinated recovery

Use through evolve for an independent recovery request, or when interrupted setup
needs coordination across tasks, artifacts or dependencies. Deliver ordered valid
continuation within the requested scope. Recovery advice can finish in the
conversation; saving or applying a repair needs an actual grant. Existing platforms
own execution, supervision and waiting. This guide adds no process manager.

## 1. Reconcile the affected work

Read the existing task definitions, current view, linked history and selected
consumer contracts. Carry the objective, target, grants, original methods,
quality criteria, reviews, consumed repair budget and stop conditions forward.
Use the caller's [method selection](../skills/harness/harness-evolve/CHANGE-FLOW.md)
before dependent authoring or repair. Keep selected standards and authority in
force until their competent owner changes them under the prior procedure.

Use [observation](../skills/harness/harness-evolve/OBSERVE.md) to correlate current
native state with recorded claims by task, artifact/revision, operation, attempt
and target. Read relevant outputs, receipts, writer/claim state and dependency
evidence. Retain event/collection time, source authority and coverage; an export
or old successful check stays historical. Unknown identity or inaccessible state
is an explicit gap, not an inferred join. Limit the map to inspected scope.

For each affected task, identify what it consumes, what it supplies, and which
conditions permit the next action. Include shared failed prerequisites and
downstream consumers of invalid output. Check independent work on its own
criteria. A stalled chain does not invalidate an unrelated accepted artifact.
Use [task workflows](team-workflow/TASKS.md) for actual ownership, transitions,
effective limits and re-entry; reconcile a prior active owner before effects.

**Done:** the map distinguishes live facts, historical claims and unknowns, and
each affected dependency has a concrete validity condition. Valid independent
work and required observations are visible before choosing repair.

## 2. Classify and order continuation

Assign a disposition per artifact/effect, with its evidence and consumer:

| Disposition | Valid next step |
| --- | --- |
| Valid completed or independent work | Preserve it and its original evidence. Continue authorized consumers whose own prerequisites pass. Complete only missing records/checks. |
| Uncertain effect | Inspect the native target, receipt/revision and audit history under the original operation identity before retry. If the available view cannot establish outcome, block the potentially duplicate mutation and name the needed observation. |
| Restoration | Recover a known valid prior state from an attributable checkpoint/source. Verify compatibility with current inputs and consumers, and scope the granted restoration before acting. |
| Recreation | Rebuild a missing/invalid output from valid inputs using its original selected methods and acceptance criteria. Retain the failed artifact/evidence and distinguish a new result from restoration of prior bytes. |
| Compensation | Offset a specific completed effect with a new effect. Establish its supported native operation, separate authority, affected parties and limits; verify both original and compensating outcomes. Proposal, execution and complete reversal are different claims. |
| Blocked or partially restored | Keep usable results and identify the exact missing fact, grant, provider, supported route or review. State which consumers remain held and who can resume them. |

Order actions by verified dependencies: reconcile uncertain effects and ownership;
retain usable independent outputs; repair the smallest failed prerequisite;
validate its result before releasing downstream work. Run independent authorized
work alongside a blocked chain when actual facilities permit. An unresolved
cycle or conflicting prerequisite needs a named resolution, not an invented order.

Reuse [tool operations](TOOL-OPERATIONS.md) for protocol/effect classification and
bounded cause-specific repair. Count prior attempts across resumes and routes.
Local operation success does not establish artifact truth, required review or
whole-chain completion. For an actual file checkpoint choice, retrieve E11 through
the entry's kit CLI and inspect the platform's real coverage. File restoration
does not undo service effects. There is no universal rollback.

**Done:** each proposed action has valid prerequisites, an applicable grant,
verification and a stop condition. Remaining blocked branches have precise re-entry;
restarting all work or resetting a spent budget is not the recovery plan.

## 3. Apply the bounded repair and reassess consumers

Use the caller's [record procedure](../skills/harness/harness-evolve/UPDATE.md)
for pre-action choice/rationale/authority, serialization, readback and scratch
scope. A recovery request does not grant lock takeover, source/config edits,
compensation, publication or deletion. Reuse sufficient existing grants; missing
authority or required capture blocks only dependent effects. For unavailable
persistence or uncertain write results, use [persistence recovery](PERSISTENCE.md)
to qualify capture and preserve the same logical record across continuation.

Reopen changing live state immediately before a dependent mutation. Reuse an
already completed effect and reconcile its record. Apply the selected local repair
only within its remaining bound. Preserve original failures and evidence conditions.
Stop on unresolved effects, refusal, unavailable required provider, no progress or
exhausted scope; retain the precise trigger instead of retrying or switching provider.

Inspect actual artifacts, native effects/counts and unchanged targets. Use
[assessment](../skills/harness/harness-evolve/ASSESS.md) against the selected
consumer criteria; check protocol validity separately from content and review.
Release a dependent task only when its own inputs, authority, required reviews
and acceptance evidence are valid. Keep regressions, uncertain comparisons and
human-only facts visible. A repaired local fixture does not qualify a real service.

**Done:** verified restoration/recreation/compensation is distinguished per target
from attempted or proposed work, and dependent consumption respects actual evidence.

## 4. Leave a resumable result

Update the existing authorized current view with the dependency order, preserved
work, changes and readback, selected contracts, consumed/remaining attempts,
partial restoration, blockers and responsible actor plus next trigger. Link original
history and source conditions; do not rewrite a failed attempt as a success. State
the actual storage survival limit and keep continuation discoverable to its consumer.

Report restoration scope and usable independent work first, then ordered remaining
actions and their prerequisites. Advice-only recovery may be complete while all
mutations remain unapplied. A saved partial recovery may be complete for the granted
work while the chain remains blocked. A fresh resume rereads changing state and
does no duplicate application or history write when nothing relevant changed.

This is inferred guidance under [spec 15, requirements 18/30/34 and A19/A20/A27](https://github.com/hanh9898/harness-kit/issues/15)
and [ticket 29](https://github.com/hanh9898/harness-kit/issues/29). Observation owns
facts, assessment owns judgments, workflow owns task flow, and tools owns local
repair. Recovery connects their actual results without replacing their contracts.
