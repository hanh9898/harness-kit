# Optional factory arrangement

Use only when the consumer selects a factory or an integrated unattended-work
arrangement. Reach this guide through setup for selected onboarding, or evolve
for independent design, assessment or authorized application. Ordinary manual
work, a task contract and a recurring deliverable do not select a factory.
The calling entry owns scope, original methods, records and whole-request completion.

## 1. Establish the selected result

Read the consumer's actual problem, task source, targets, existing facilities,
prior choices and grants. Identify whether the result is a design in the
response, a saved arrangement, an authorized application or an operational
assessment. Preserve adequate project choices; missing choices stay explicit.
A design-only request authorizes neither a save nor activation. Use a scoped
example only with an explicit learning goal and effect grant; do not invent a
production workload or choose a consumer orchestrator on their behalf.

Use the entry's [method composition](../skills/harness/harness-evolve/CHANGE-FLOW.md).
When the owner explicitly selects original software-factory, load its actual
source and applicable references through the permitted provider route. Preserve
its task/service questions and completion requirements. Respect explicit-only
invocation: selecting this kit capability does not unlock a restricted child
skill. A required unavailable method blocks dependent work with its exact
continuation; source-grounded kit guidance is not a manual substitute. Agent-read
authoring also retains the selected original writing discipline.

**Done:** the requested result, selected original methods, actual authority and
application boundary are clear. Independent read-only findings can remain useful
while a required source, product choice or effect is blocked.

## 2. Connect services and work acquisition

Name the consumer-selected product and actual access route for each service:
ticket tracker, ticket source, git host, orchestrator, runner and observability
platform. One product may fill several roles. A deliberate absence of a separate
observability platform is valid when the existing run view suffices. Record
missing choices and unsupported slots as design gaps; do not label an incomplete
service arrangement finished. A non-code or local rehearsal may deliberately
leave a service unused, explaining the resulting limit on the full factory design.

Separate proposed service wiring from installed, configured and observed use.
Reuse existing facilities through [tool operations](TOOL-OPERATIONS.md), checking
meaningful inputs, outputs, effects and actual permissions for each required
operation. A service name or available executable is not integration evidence.

Use [task contracts](team-workflow/TASKS.md) for definitions and work items, and
its [tracker branch](team-workflow/TRACKERS.md) when source and committed-work
storage differ. Connect each source identity to one authoritative work item,
the commitment decision, dependency/entry checks, owner/claim and capacity.
Read-only sources remain unwritten. Explain source deduplication and how repeated
triggers find the existing item instead of creating another. Verify that the
next actor can retrieve the authoritative definition, inputs, policies and
continuation. For disposable runners, identify and verify the retained storage
path; local uncommitted files alone are a readiness gap.

**Done:** every service slot and work-acquisition edge is assigned or explicitly
blocked, with authoritative locations, access, commitment and duplicate handling.
A list of products without these connections is not the operating arrangement.

## 3. Connect tasks, roles and controls

For each selected task, use the existing contract to connect its trigger and
entry conditions, inputs and revisions, methods and service reads/writes,
outputs and testable completion, next task or termination, human re-entry and
duplicate-run control. State the trigger's producer and the next consumer's
acceptance condition. Preserve task identity across attempts. Reuse definitions
when steps and completion match; separate materially different work.

Use [team responsibilities](team-workflow/TEAM.md) for actual actors, context,
review competence and independence. Use [authority](authority/DESIGN.md) for
concrete permitted/blocked choices and effects. Task stage, function ceilings,
actual grants and native enforcement are separate. Name which actor may propose,
decide, execute, review and resume each transition; an unfilled reviewer role is
a dependent gap, not a completed review.

Apply [selected flow and brakes](team-workflow/FLOW.md). Resolve all ten flow
functions there to a project value/rationale and mechanism/evidence, or a justified
non-use under its condition. Preserve selected stage and stage-raising approval,
review-stop bounds, reversibility approval, andon response and human escalation.
Resolve shared policy and task exceptions under the prior authority; neither a
new contract nor a successful rehearsal can waive them. In particular:

- Competing actors require a common effective claim before taking the same item.
- Unattended work requires an off switch, stop bound and visible give-up. Distinguish
  preventing new runs from stopping active work, with actual scope and coverage.
- Outputs that can start runs require a trigger-loop guard. Distinguish causal
  deduplication from a finite retry cap; verify both where selected.
- Retain deterministic checks, separate automated review and human review where
  selected. Self-checks cannot stand in for either independent or human review.

When a task needs a human, end its run with the exact decision/evidence, responsible
human, preserved work and next authorized trigger in the existing tracker/git
host or orchestrator. Human re-entry starts a new run that reconciles live state;
it does not keep the old run waiting. A saved handoff is not proof of receipt.
Start with the selected narrow/throttled trigger; broader activation requires
its own authority and evidence. The kit supplies no scheduler or waiting service.

**Done:** a new actor can follow every transition without guessing its authority,
completion, stop or re-entry condition. Missing controls block the dependent
unattended path; supervised fallback establishes only supervised use.

## 4. Join observation, recovery and readiness

Use [observation](../skills/harness/harness-evolve/OBSERVE.md) to connect task,
work item, run/attempt, target/revision, trigger and native result identities with
time, source and coverage. Keep unknown cost, stale status and conflicting facts
visible. Observability-platform output informs the operator; when the selected
original factory contract requires choices through tracker/git-host state,
preserve that path rather than letting logs silently become a trigger authority.

Use [coordinated recovery](RECOVERY.md) for failed prerequisites, uncertain effects
or interrupted runs. Inspect actual effects and prior ownership before retry;
preserve valid independent results, original failures and consumed bounds.
Connect each repair's verification to the downstream task's acceptance, with
restoration, recreation and compensation distinguished. A human handoff identifies
the exact changed fact/grant/review that permits re-entry. An exhausted loop stays
exhausted across new runs. Stops and revocations remain effective immediately.

Assess each target/path with [criterion assessment](../skills/harness/harness-evolve/ASSESS.md):

| Claim | Evidence required |
| --- | --- |
| Design delivered | Connected services, accessible or precisely specified contracts, roles, controls, observation/recovery and all task/source questions answered; unresolved choices identified |
| Authorized application | Actual prior grant/procedure, selected methods/standards, required capture and readback, inspected changes and protected scope, discoverable continuation |
| Observed supervised use | A bounded actual task reaches its applicable done criteria under recorded local conditions; unmet review and downstream gates remain visible |
| Observed unattended readiness | Representative authorized operation through real triggers/acquisition, accessible retained contracts, claims where needed, stop/off-switch/loop mechanisms, reviews/handoffs and recovery, with evidence for the claimed target and failure coverage |

Give an evidence-backed disposition per path, not one green label for the assembly.
Documentation, configured caps, synthetic fault reports and manual fallback do not
establish deployed unattended readiness. If no unattended run was observed, say so.
Useful design or local application can finish while deployment remains blocked.

## 5. Apply only the granted slice and hand over

For an authorized application, use the calling entry's
[record procedure](../skills/harness/harness-evolve/UPDATE.md): prior authority,
pre-effect capture/readback, canonical serialization, scratch boundaries, history
and actual effect inspection. Apply at the selected interval, normally future
runs or an expressly granted reconciliation point. Preserve one-call scope;
lasting permitted artifacts do not supply future-call or standing automation grants.

Exercise the smallest representative initial use authorized by the request.
Inspect the result and unchanged targets, method loading, selected controls and
remaining review gates. Keep failed attempts and their original conditions.
Record actual host/model/provider/resource versions, grants, selected/applied/
reviewed/observed distinctions, remaining work and next trigger. State storage
survival and observation limits. On resume, reconcile live facts first and avoid
repeating completed effects or unchanged history. Read-only design finishes in
the response without creating records.

**Done:** the selected result is independently useful and assessed. The consumer
has a connected arrangement, completed authorized effects or precise dependent
blockers, and a concrete continuation. Source provenance is in [FACTORY-SOURCES.md](FACTORY-SOURCES.md).
