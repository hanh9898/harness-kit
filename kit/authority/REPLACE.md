# Governed replacement

Read for a core obligation, selected rule/standard/provider replacement, nested
harness change or changed application boundary. Use this branch inside
[authority design](DESIGN.md) and [consumer adoption](../../skills/harness/harness-evolve/ADOPTION.md).
It supplies the change decision; those workflows retain the requested result,
original-method selection, actual effect checks and record procedure.

## 1. Resolve the prior authority and minimum responsibility

Inspect the actual affected harness, effective contracts, prior choices and
procedure, current grants and stop sources. Identify the competent design authority
for **each** harness. Library-edit permission covers material, not adoption.
Containment, file ownership or an outer harness grant cannot revise a separately
governed nested core. Ordinary nested invariants remain selected consumer contracts;
their location does not make them universal obligations.

For each proposed fixed core obligation, record:

- The user guarantee that omission would break.
- Why an existing selected contract or platform facility cannot adequately preserve
  that guarantee. If one suffices, keep the responsibility there.
- Only the minimum necessary fixed responsibility, and why narrower alternatives
  are insufficient. Distinguish that responsibility from a chosen implementation.

Use the same criterion when reducing or replacing an existing core. Competent
harness design authority may revise it with rationale and impact; the criterion
is not a permission grant or a reason to erase effective obligations. Account for
consumer contracts, customizations, review, provider prerequisites and affected
use/evidence. For a provider replacement, qualify the actual consuming contract
and invocation route; a matching name, readable file or permission to select it
is insufficient. Preserve required original-method discipline or establish the
explicit compatible replacement before dependent construction.

**Done:** each target has a justified core or selected-contract disposition and
an actual prior authority/procedure, or a precise dependent blocker. Reuse adequate
prior choices; do not reopen settled choices or invent a new approval gate.

## 2. Select the application boundary

Resolve the change under grants and procedure in force **before** adoption. The
candidate rule cannot approve itself, change its own approver or supply missing
scope. Separate permission to save/install material from permission to use it in
an active task or change persistent permissions. A one-call grant can authorize
lasting or shared effects in its actual scope; persistence needs no second grant.
It grants neither later calls nor persistent permission changes outside that scope.

Record the selected boundary per consumer, including work still using older choices:

| Boundary | Required disposition |
| --- | --- |
| Future run (ordinary recommendation) | Save the authorized selection for later runs. Keep current work on its pinned choices only while accessible, valid and authorized. A later run rechecks actual grants before effects. |
| Explicit reconciliation point | Identify the named point and affected work. Inspect completed and pending effects there, check compatibility, then switch only the authorized remaining work. Preserve valid completed effects and prior history. |
| Qualified live migration | Establish a safe point with actual in-flight work and writers accounted for, available old/new definitions and providers, compatible remaining inputs/outputs, scoped migration authority, required durable capture and usable stop controls. Exercise the needed transition/checks through existing facilities; state what was actually demonstrated. If those conditions cannot be established, block live adoption and propose an authorized later boundary. |

If prior choices are inaccessible, inspect authoritative history and live effects.
Retain unknowns; neither reconstruct the missing rule from a label nor silently use
the new rule. Block work that depends on the unavailable definition. An independently
qualified replacement can proceed under its own prior authority and explicit
boundary if that decision does not require the missing information. Complete
independent permitted work and name the exact recovery or replacement trigger.

Stop/revocation applies immediately to affected actions, regardless of a pinned
version or promised interval. Recheck the live authority/control source before
dependent effects and respond to a received stop without finishing the old plan.
Stop further effects; use an existing authorized cancellation mechanism for work
in flight and report its actual result or limit. Revocation does not itself grant
rollback, deletion, new record writes or another call. Preserve existing effects
and report uncertainty when inspection or compensation is not authorized.

**Done:** selected versions, permitted effects, time of use, still-running work and
stop disposition are unambiguous. A blocked live change is not reported as applied.

## 3. Capture, apply and verify the bounded result

Use the existing [record procedure](../../skills/harness/harness-evolve/UPDATE.md)
for serialization and recoverable pre-action capture/readback of the prior authority,
minimum-core rationale where applicable, impact, compatibility, boundary and pending
effects. Reuse adequate references. Preserve exact prior material needed by continuing
work and history before replacing it; keep selection separate from active use.

Under that procedure, reopen changing grants, controls, contracts and live targets
before each dependent effect. Apply only the authorized compatible action. Inspect
actual target bytes and operation results, protected consumers and any changed
permission state. Check selected provider loading/invocation for the affected use.
A saved policy is not evidence that a host enforces it or that an active run changed.

Record actual per-target application and timing, observed use/checks, failures and
remaining prerequisites. Keep decision review and outcome claims separate. For a
fresh continuation, reconcile existing effects/history and the current call's grants;
complete only missing authorized work. An unchanged completed request adds no effect
or duplicate history. No lifecycle engine or universal rollback is required.

**Done:** the current view and linked history explain who authorized what under
which prior procedure, when it became effective for which consumer, what actually
happened, and the next trigger. Qualification covers only observed conditions.
