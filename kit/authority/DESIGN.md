# Authority design and effect grants

Deliver a usable model, a delegated-choice review/calibration result, or a concrete
effect decision through setup/evolve. A model-only request can finish without
adoption, team setup or a factory. For settled terminology read the
[authority glossary](GLOSSARY.md); for provenance or a disputed model fact
read [sources and certainty](SOURCES.md).

## Establish the applicable authority

Read the requested result, current choices, actual grants and native constraints.
Identify the target, effect, actor, grant issuer, scope, duration and revocation
source. Reuse sufficient prior authority. Identify the procedure already in force
for adopting a change and the competent authority over each affected harness.
An outer harness or library editor does not gain authority over another harness's
core through containment or an editable file.

Keep task adoption stage separate from function ceilings. Reuse the selected
[task contract](../team-workflow/TASKS.md) for stage, transitions and review timing,
and [team responsibilities](../team-workflow/TEAM.md) for reviewer identity,
context, authority and independence. Selected stage-raising approval, reversibility,
brake and stop controls still bind. A high function ceiling cannot raise stage,
waive required review or create an effect grant.

**Done:** effective choices and prior change authority are identified for each
proposed target, with unresolved conflicts blocking only dependent work.

For core obligations, selected rule/standard/provider replacement, nested governance
or application-boundary changes, read [governed replacement](REPLACE.md) before
deciding or applying the change.

## Construct explicit ceilings

The recommended assembly uses Parasuraman–Sheridan–Wickens (PSW), Shavit-inspired
recording/review and Lee–See-informed calibration. Read [the scale](SCALE.md) when
constructing or changing ceilings. Define each function separately for the actual
task, splitting materially different choices such as draft wording and release:

| Function | Question for the consumer |
| --- | --- |
| Information acquisition | Which sources may the agent obtain, select or filter, and what remains visible to the human? |
| Information analysis | Which transformations, interpretations and uncertainty judgments may it produce? |
| Decision selection | Which alternatives may it propose, narrow, recommend or choose, and who decides? |
| Action implementation | Which chosen actions may it execute, on which targets, with which intervention and reporting conditions? |

For each function state the concrete allowed behavior, retained human control,
selected level and any adaptation of its meaning, excluded effects, relevant
prerequisites, evidence basis and limits. A ceiling is a maximum within scope,
not a command to automate to that maximum. Mark proposed ceilings as proposed.
Preserve already-authorized work while a narrower missing choice is unresolved.

Qualified alternatives include a named different scale or explicit task-specific
rules without numbers. Compare the alternative's actual definitions against these
four functions, retained human choices, grants, logging/review, stop controls and
consumer evidence. Record rationale, gaps and prior adoption authority. Delegation
Poker may support human discussion but needs explicit actor perspective and these
mappings; matching numbers do not establish equivalence or compatibility.

**Done:** a consumer can resolve concrete allowed and blocked cases without guessing
from a number. Source-backed design is separate from demonstrated operation.

## Resolve a concrete effect

1. Describe the actual effect: operation, target, audience, persistence and possible
   indirect effects. Include helper files and permission changes when relevant.
2. Match it to the applicable grant and current ceiling, stage, selected controls
   and native constraints. Recheck changing authority immediately before effects.
   Technical capability or an approval setting is not user authorization.
3. If sufficient, proceed under the prior procedure at the granted time. Lasting
   effects within a one-call grant need no extra approval merely for persisting;
   that grant supplies no standing authority for later calls.
4. If scope is missing, revoked, conflicting, or a required review/control cannot
   operate, stop that effect. Name the exact missing condition and responsible
   authority. Continue independent permitted work and use the existing handoff;
   do not create a waiting service, blanket approval click or silent timeout grant.
5. For selected consequential-action logging, use the existing
   [record procedure](../../skills/harness/harness-evolve/UPDATE.md) to capture and
   read back rationale, alternatives, scope and authority before effects. Inspect
   resulting state before recording application/outcome or retrying uncertain work.

Label an instruction as an instructed restriction. Claim native enforcement only
for the mechanism, operation and conditions actually exercised. A successful
self-restraint case proves neither a sandbox boundary nor resistance to a
noncooperating actor. Reuse [tool operations](../TOOL-OPERATIONS.md) for a needed
native-control check; do not infer mechanism support from a model definition.

**Done:** the proposed effect has an actionable permitted or blocked disposition,
its actual effects and untouched scope are inspected when execution is requested,
and remaining prerequisites and the next trigger are discoverable.

## Review, calibrate and reconcile

For a delegated-choice review or calibration request, read [REVIEW.md](REVIEW.md).
For legacy four-axis/seven-step content, first read its migration notice in
[delegation.md](../delegation.md). Preserve the old source, uncertainty, valid
applied work and personal customization. Compare effective old rules with the
selected model function by function; do not convert seven numbers into ten or
carry old heuristics forward by default. A currently selected legacy obligation
still binds until competent replacement under the procedure that preceded it.

Adopt only within existing grants and selected timing: ordinarily future runs,
an explicit reconciliation point, or a qualified live migration. The replacement
cannot authorize its own adoption. Revocation and stops take effect regardless of
an older definition's interval. Record supersession, retained choices and unresolved
consumers; editing supplied guidance does not migrate a user's applied policy.
