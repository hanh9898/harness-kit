# Sources and work trackers

Read when selecting where committed work is governed or when a task reads external tickets. This is inferred guidance implementing the [accepted tracker decision](SOURCES.md). Separate the origin of a request from authority over the work accepted from it.

## Choose with actual access

Inspect each source's granted and available **read, comment and create** operations separately, plus any requested state-change operation. Record what is observed, granted, denied or untested. An accessible issue URL or a source-key link grants no write authority. Preserve read-only sources. A missing required source blocks the dependent conclusion; preserve an unverified proposal or independent work and name the missing access rather than inventing its facts.

Compare all four alternatives against write access, survival after runner disposal, multi-machine use and audience. Reuse a suitable current choice without a new storage interview.

| Alternative | Fits when | Limits to resolve |
| --- | --- | --- |
| Shared project tracker | Work belongs to the team and actual write authority exists | Check permitted operations and audience; source read access does not imply this grant |
| Personal remote tracker | Work is personal, cross-machine, or uses disposable runners | Check actual account/access, privacy and handoff audience; a selected remote name is not a verified integration |
| Ticket files committed with the project | Git-backed portability and review fit the work | Check commit authority and repository retention/availability after disposal; local commits without a retained/shared copy do not prove multi-machine survival |
| Local uncommitted ticket files on a persistent runner | Personal local work deliberately accepts local durability | Record the durability deviation, exact persistent home and access route; runner disposal loses these by assumption. This is not a substitute for a selected stronger survival guarantee |

A safe unavailable alternative may be recommended conditionally; it is not operationally ready. Never create a real project/personal tracker or write a source merely to test access without a grant.

## Declare and use one authority at commitment

For work crossing a chosen commitment point, declare **one authoritative committed-work tracker**, its owner, authoritative location, access instructions, operation permissions and durability/coverage limits. Keep source keys and source links as references. Other views are exports or caches that name that authority. A purely interactive request without commitment does not require a tracker; durable harness-change records remain governed by the calling workflow's separate record contract.

Make the declaration discoverable through existing project guidance and the selected methods' tracker guide. Tools owns configuring and verifying the integration; tasks consume generic fetch, publish, comment, claim and resolve operations. An unavailable operation remains unavailable: use an authorized adequate alternative or stop its dependent work. Do not implement an adapter just to express this contract.

For application, inspect actual effects using the selected native/file operation, read back work state, and preserve source bytes/remote state within the checked scope. Verify identity, result, failed writes, claim/exclusion behavior where selected, and continuation after interruption. Distinguish source read success, tracker-write success and actual durability. A local fixture of a remote service qualifies no remote provider.

**Done:** committed work has one accessible authority within the actual grant, sources retain their real restrictions, and the chosen durability and audience limits remain visible to later actors.
