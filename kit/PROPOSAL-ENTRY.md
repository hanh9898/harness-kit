# Proposal-first entry

Apply this guard to the six Harness and Bot entry skills and every discovery
topic. It governs how a request starts, not what the caller may do.

## Direct request

If the user gives a clear request, or an authorized internal caller gives a
concrete operation and scope, go Direct: 0 proposal steps. Do not pitch options
or ask the caller to select it again. Use the skill's own clarification gate
for missing material details; do not turn a partial request into an unrelated
proposal. Keep its route, scope and effect gates.

## No request: research silently

Before asking anything, with no progress narration, read only enough to
cross-check a useful lead. Use related chat or sessions, the repo and its
history, the bound store, or connected integrations such as Slack or Linear
only as relevant and within the current ACL. Reuse evidence while it is
current. Do not quote private chat or disclose private channel names. Setup
and discovery topics use only intent, stack, settled choices and static facts;
use repo history only for static provenance, not operational history. Do not
probe Inbox or Memory routes that lack opt-in.

Use only operations proven read-only on the actual route. Until selection:
0 writes, including files, directories, WAL/SHM, Git or config edits, durable
drafts, checkpoints and cursors. Do not create PRs, tickets or cards; install
or register skills; claim work; grant, sync, upload, notify or schedule.
An old grant is not an exception. If a read cannot meet these limits, skip it;
do not widen scope or use an unqualified substitute to find evidence.

## First response

Use about 60 words and at most 8 short lines. Offer 1–2 high-impact actions:
a title, the benefit and verified evidence in parentheses. Include counts
only when verified. Offer one when only one qualifies; do not pad with
code-hygiene work. If none qualify, return NoProposal: say there is not
enough evidence and invite a request without offering guesses. Include an
exact connection link only when evidence shows the team uses a missing
integration and connecting it would unlock a concrete benefit. Do not
connect it yourself.

## Selection (H1)

Use the literal titles and `Something else` as the choices. Allow multi-select
when the proposals are compatible and the host supports it; handle each
selected intent. If there are no controls, use the same labels inline,
not an Inbox card or outbound message. `Something else` or an edit opens a
request only when it supplies concrete intent. Decline, silence and an
ambiguous response open nothing, including on resume.

Selection establishes intent, not permission to create a record, install or
execute. Both entry routes still require the destination's exact grant and
the skill's own checks before any effect. A read-only request remains
read-only even with a prior grant. Chat, @mentions and Inbox replies are
interactive input, never background wake triggers.
